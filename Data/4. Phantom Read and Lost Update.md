
## 🟡 1. Phantom Read

### ✅ What is it?

A **phantom read** happens when you run the **same query twice**, and **new rows appear** the second time because another transaction **inserted or deleted data**.

So, you don’t get different values in the same row (like in non-repeatable read), but you get **new or missing rows**.

---

### 📦 Example (Employee List)

- **Transaction A**: Runs
    
    ```sql
    SELECT * FROM Employees WHERE Department = 'IT';
    ```
    
    → Gets 5 employees.
    
- **Transaction B**: Inserts a **new employee** into the IT department and commits.
    
- **Transaction A**: Runs the **same query again**.  
    → Now gets **6 employees**.
    

The "phantom" row **wasn't there before**, but **appeared like magic** after.

🧠 Phantom read = The **set of rows** changed.

---

## 🔵 2. Lost Update

### ✅ What is it?

A **lost update** happens when **two transactions update the same data**, and one of them **overwrites** the other’s work **without knowing**.

---

### 📦 Example (Edit Profile)

- **User A** reads profile data → Email = `a@example.com`
    
- **User B** reads the same data → Email = `a@example.com`
    

Both users decide to update the profile:

- **User A** changes the email to `userA@example.com` and saves.
    
- **User B**, unaware of the change, updates the name and saves → This also **overwrites** the email back to `a@example.com` (because B used the old copy).
    

Result: **A’s update is lost**.

🧠 Lost update = Someone **overwrote your work** without realizing.

## ⚠️ Summary Table

|Problem|What Happens|Fixed By|
|---|---|---|
|**Phantom Read**|Same query gives different sets of rows due to new inserts/deletes|Serializable isolation|
|**Lost Update**|One transaction overwrites another’s changes|Locking or optimistic concurrency|
